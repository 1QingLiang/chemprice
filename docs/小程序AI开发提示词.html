P0 · 总纲（必须第一条发送）

你是资深微信小程序前端工程师。现在要为一个**已上线的化工价格数据平台 ChemPrice** 开发微信小程序端。

## 一、最重要的约束：后端已存在，不要重写

后端是 Spring Boot 3.5.6（Java 21）+ MySQL，**已经完整上线**，端口 9000，nginx 反代。
小程序端**只写前端**，需要新接口时先提出来，不要假设后端可以由你随意改动。

技术栈现状（Web 端，供你理解数据结构）：
- Vue 3.4 + Vite + Pinia + Vue Router 4
- ECharts 5.5.0（图表）、Element Plus（组件）
- axios

## 二、你的技术选型

⚠️ 必须使用 **uni-app（Vue 3 + TypeScript）**，理由：语法与现有 Vue3 代码接近、可复用部分逻辑、
一套代码可编译到微信小程序 / H5 / App。

- 构建：`@dcloudio/uni-app` 最新稳定版
- 语言：TypeScript（严格模式）
- 状态管理：Pinia
- 请求：封装 `uni.request`，**不要用 axios**（小程序环境不支持 XHR）
- UI：优先 `uni-ui`，必要时自绘
- 图表：`lime-echart` 或 `echarts-for-weixin`（按需引入 ECharts 模块，禁止全量引入）
- 地图：微信原生 `map` 组件 + 自绘 canvas 着色，或 ECharts geo（见 P2）

## 三、⛔ 六条红线（违反即返工）

### 红线 1：业务错误码判断，绝不能只看 HTTP 状态码
后端返回结构：`{ code: number, message: string, data: T }`
**业务错误也会以 HTTP 200 返回！**
- ✅ 必须：`if (res.data.code !== 200) { ... }`（成功码以后端实际为准，先在 `/api/auth/me` 上验证）
- ❌ 禁止：`if (res.statusCode !== 200)`
这条是踩过坑的，网上搜到的"小程序请求封装"模板基本都是错的。

### 红线 2：权限判定必须调用后端接口，禁止前端自行推导
标点地图可用性**只能**消费 `GET /api/enterprise-map/access` 的返回字段：

{ switchOn: boolean, enabled: boolean, expireDate: string|null, daysLeft: number|null, expired: boolean, reason: string }

- ❌ 禁止在前端写 `switchOn && !expired` 之类的组合判断
- ❌ 禁止前端自行计算剩余天数（用后端 `daysLeft`）
- 前端只负责把 `enabled=false` 映射成"需开通"、`expired=true` 映射成"已到期"

### 红线 3：注意交易日，非交易日不能报异常
平台有交易日历。法定节假日 / 休市日**不更新行情数据**（爬虫不跑）。
- 页面必须展示"数据截止 X 日"，用后端返回的 `data_date`
- ❌ 禁止把"数据日期不是今天"渲染成错误 / 警告
- 存在调休补班日（周末照常开市），**日期运算判断不了**，一切以数据为准

### 红线 4：禁止暴露数据供应商名称
全站（含分享卡片、订阅消息、帮助页）**不得出现数据源供应商名称**（具体名称不问，照此执行即可）。
统一口径文案：`数据来源：ChemPrice 化工价格平台`。
❌ 具体禁用名单会在你交付时由我核对，你只需保证所有来源文案都用上面这一句。

### 红线 5：合规红线（服务类目相关，内容审核会挂）
小程序申报类目是「商业服务 → 信息查询」。全站文案**禁止**出现：
`投资` `理财` `期货` `证券` `荐股` `涨跌预测` `行情分析报告` `交易信号` `抄底` `加仓`
✅ 允许用语：`原料价格` `报价点` `价格走势` `数据查询` `仅供参考`

### 红线 6：包体与性能
- 主包 ≤ 2MB，分包总计 ≤ 20MB
- 地理数据（GeoJSON）**必须分包或按省懒加载**，禁止一次性引入全国市级数据（Web 端那个文件 2.38MB，直接搬过来必然超限）
- ECharts **必须按需引入**（只引 line / bar / heatmap / tooltip 等实际用到的模块）

## 四、认证方式

- 小程序登录：`wx.login()` → `code` → `POST /api/wx/login` → 返回 JWT
- 后续请求带 `Authorization: Bearer <token>`
- JWT 过期处理：拦截到 401 → 静默重新登录一次 → 重放原请求；再失败才跳登录页
- ⚠️ Web 端用的是 HS256 JWT，小程序端**不需要也不允许**接触签名密钥

### ⚠️ 关于 `/api/prices` 的重要提示
这是最核心也最"重"的接口，底层是三张亿级表：
- `market_price`（约 651 万行）
- `enterprise_price`（约 736 万行）
- `international_price`（约 65 万行）

慢查询与分页是历史重灾区，后端已做优化。你调这个接口时必须：
1. **必须传分页参数**，禁止一次拉全量
2. **必须容忍慢响应** —— 前端超时不要设 10 秒以下（曾因 10s 超时静默 abort 导致页面一直转圈）
3. 「全部类型」查询是后端 `UNION ALL` + SQL 层 `LIMIT/OFFSET`，**不要在前端做二次分页或排序**
4. 看到响应慢先怀疑网络与超时设置，**不要**改成分页拉全量再前端切片

## 3. 标点地图 `/api/enterprise-map`（⭐ 核心功能）
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/enterprise-map/access` | ⭐ **权限判定唯一入口** |
| GET | `/api/enterprise-map/points/varieties` | 可选品种（256 个） |
| GET | `/api/enterprise-map/points/overview` | 总览（可传 province 下钻） |
| GET | `/api/enterprise-map/points/cities` | 市列表（传 province） |
| GET | `/api/enterprise-map/points/detail` | 报价点明细（传 province / city / varietiesId） |
| GET | `/api/enterprise-map/points/matrix` | 省份×品种矩阵（可传 province、topRow、topCol） |

数据规模：**2,288 个报价点、30 个省级行政区、282 个城市、256 个品种**。
数据源是预计算表 `enterprise_point_stat`（每日 06:40 刷新），响应很快。

### ⛔ 三个必须知道的坑
1. **`varietiesId = 0` 是"全部品种去重"行**。查询"全部品种"时必须传 0，**不能**跨品种把各省数字相加（会重复计点）。
2. **`/points/detail` 返回的是点级粒度**，不要拿汇总口径的数据去渲染单点。
3. 部分报价点**只能确定到省级**（城市无法可靠判定）。页面必须保留提示："另有 N 个报价点仅到省级"。

P2-B · 标点地图（最难，单独一轮）

开始实现 M2：标点地图。这是整个小程序的核心差异功能，也是最难的一块。

功能：
1. 页签一「企业分布」：全国地图着色（按报价点数）
2. 页签二「产品分布」：可切换 256 个品种
3. **逐级下钻**：全国 → 省 → 市 → 报价点列表，带面包屑与返回
4. 只到省级的报价点要单独提示（不参与城市下钻）
5. 三张分析图：TOP10 条形（可点击下钻）、集中度帕累托、省份×品种矩阵

⛔ 权限三态（必须严格区分，这是踩过坑的）：
- `权限未知（接口未返回）` → **不打任何标记**
- `未开通（enabled=false）` → 琥珀色「需开通」+ 三步开通引导
- `已到期（expired=true）` → 红色「已到期」+ 续期引导
- 未到期但 `daysLeft <= 7` → 提示剩余天数
判定**只能**消费 `/api/enterprise-map/access` 的字段，禁止前端推导（红线 2）。

⛔ 地图技术难点（重点解决）：
- 全国市级 GeoJSON 有 2.38MB，**绝不能进主包** → 用分包，或按省懒加载
- 移动端手势冲突：地图缩放/平移会误触发下钻 → **下钻只响应点击省市区域，禁止双击下钻**
- TMap（腾讯地图）在小程序里若使用，注意其内联层级；Web 端曾因内联 z-index 全覆盖导致按钮点不到，小程序同样要**真机**验证可点性
- 矩阵热力图在手机上放不下 → 横向滚动 + 固定首列

⛔ 必须真机验证：
- 每个可点元素都要确认真能点到（不能用"看起来对"代替）
- 下钻后地图能正确缩放居中
- 返回上一级的三条路径（地图按钮 / 侧栏按钮 / 面包屑）都要通

交付：代码 + 真机测试截图 + 三个坑的处理说明。

P3 · 商业化（主体确认后发送）

⛔ 合规：

- 不得出现投资类表述（红线 5 继续有效）

- 地图：`/api/enterprise-map/points/{varieties|overview|cities|detail|matrix}`（`varietiesId=0` 表示"全部品种去重"，不可跨品种相加）
- 供需：`/api/demand`（求购数量必填、供应选填）

MVP 页面：登录 / 看板 / 商品列表 / 商品详情 / 涨跌排行 / 标点地图（全国→省→市→报价点下钻）/ 供需广场 / 我的。
每页必须有 4 种状态：loading / 正常 / 空 / 失败+重试。

第一步只输出技术方案与目录结构，不要写代码。

使用说明（给你自己看的）

顺序发送内容预期产出
1P0 总纲AI 复述约束，确认理解
2P1 接口契约页面清单、目录结构、请求封装设计、需补接口
3P2-AM1 只读骨架可运行代码
4P2-BM2 标点地图（含真机截图）
5P2-CM3 供需 + 消息
6P3M4 订阅付费

注意事项：

  1. 先 P0+P1，等它输出方案再放行代码。一次性全发，AI 容易跳过设计直接写垃圾代码。
  2. P2-B 是唯一需要真机反复验证的一环，别接受"看上去对"。
  3. 提示词里刻意不写数据库密码、JWT 密钥、AppSecret —— 凭据一律运行时通过环境变量传递，绝不落进提示词或代码。
  4. 交付后必须人工核对：红线 1/2/5 是最容易反复犯的三条。
